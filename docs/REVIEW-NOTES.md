# 审查结论

云同步代码经过三轮独立审查。这份文档记录**判定为不成立的结论**及其证据，以及反复出现的缺陷模式。改动这块代码前先读，以免重新"修复"已经查证过的东西。

## 已判定不成立

### WinHTTP 会丢弃查询串

三轮审查里报了三次，判定为**不成立**，但代码仍做了防御性加固。

结论认为：`WinHttpCrackUrl` 在不提供 `lpszExtraInfo` 缓冲区时会丢弃查询组件，因此 `S3Backend::List` 发出的请求不含 SigV4 所签名的查询串，签名必然不匹配，S3 拉取必然失败。

反证是一个能区分两种情形的实验。往桶里放一个前缀之外的对象 `zzz-outside/decoy.userdb.txt`：

- 若查询串到达服务端，前缀过滤生效，诱饵对紫毫不可见，拉取正常
- 若查询串被丢弃，服务端返回全部对象，诱饵的键因不匹配前缀而被 `substr` 截出错误的名字，随后 `Get` 必然 404，整个拉取失败

实测结果是诱饵不可见且拉取正常。此外还有一个更直接的判据：签名覆盖规范查询串，服务端收不到查询串时重建出的签名必然不同，会返回 403 而非 200。

尽管如此，`HttpRequest` 现在显式请求 `lpszExtraInfo` 并拼回请求目标。理由不是结论正确，而是这个行为在文档里没有保证，而 SigV4 恰好签了查询串——一旦哪天行为改变，症状会是所有列举一齐签名失败。消除脆弱依赖比争论当前行为更有价值。

### 卸载时 `RegDeleteKey` 会摧毁另一个发行版

成因判定有误，但**相邻的问题真实存在**且已修复。

结论认为 `imesetup.cpp` 中 `RegDeleteKey(HKEY_LOCAL_MACHINE, RIME_REG_KEY)` 会删掉共享的 `Software\Rime` 父键，连带毁掉官方小狼毫。实际上 Win32 的 `RegDeleteKey` 在目标键仍有子键时会失败，因此另一个发行版存在时它删不掉父键，反而是在清理空父键。

真正危险的是 NSIS 的 `DeleteRegKey`，它**默认递归**。安装脚本里那两处已改为只删本产品分支，父键改用 `/ifempty`。

### S3 端点中的端口

结论认为 `HostFromEndpoint` 返回的 host 含端口，会传给 `WinHttpConnect` 而导致连接失败。实际上该结果只用于 SigV4 的规范 host，连接用的是 `HttpRequest` 内部独立解析的结果。而 SigV4 要求签名的 host 与实际发出的 `Host` 头一致，非默认端口本就应当保留。

但它点到一个真实边界：显式写出与协议默认值相同的端口（`https://host:443`）时 WinHTTP 会将其从 `Host` 头中省略，签名就对不上。现在只剥离这种重复端口。

## 反复出现的缺陷模式

### 「没有数据」与「拿不到数据」共用一个返回值

连续两轮在同一模式上出问题，都属数据丢失级：

- `SyncBackend::Get` 原先返回 `bool`，404 与网络故障不可区分。网络抖动会被当作「尚未存储数据密钥」，随后发布的新密钥覆盖旧密钥，**所有已加密快照永久无法解密**。
- `ReadFileBytes` 原先在「文件为空」与「文件打不开」两种情形下都返回空缓冲。后果同上，另外还可能把空内容推送上去覆盖云端的好快照。

现在前者返回 `FetchResult{ kOk, kNotFound, kError }`，后者单独上报失败；「数据密钥读回来是空的」判定为存储损坏而非缺失。

**新增任何后端或存取路径时，检查这两种情形是否可区分。**

### 验证只证明了结果，没证明路径

一处硬编码让紫毫读取了官方小狼毫的注册表键。同步测试全部通过，因为两个键**恰好指向同一个目录**——缺陷被完全掩盖。

后来的验证改为把两个键指向不同位置再观察文件落点。**设计验证时要能区分「碰巧对」和「真的对」。**

### 改动散落在肉眼扫不到的地方

更新源的地址存在 `.rc` 里，是十六进制裸字节，扫代码看不出来。因此改完注册表路径之后，紫毫仍会去下载**官方小狼毫**并覆盖安装自己。

现在改为在代码中显式设置 feed 地址，其优先级高于资源，资源里的旧地址不会被意外采用。共存所需的全部标识清单见 [DESIGN.md](DESIGN.md)。
