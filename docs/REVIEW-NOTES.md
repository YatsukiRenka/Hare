# 审查结论

云同步代码经过独立审查。这份文档记录**判定为不成立的结论**及其证据，以及反复出现的缺陷模式。改动这块代码前先读，以免重新"修复"已经查证过的东西。

## 已判定不成立

### WinHTTP 会丢弃查询串

三轮审查里报了三次，判定为**不成立**，但代码仍做了防御性加固。

结论认为：`WinHttpCrackUrl` 在不提供 `lpszExtraInfo` 缓冲区时会丢弃查询组件，因此 `S3Backend::List` 发出的请求不含 SigV4 所签名的查询串，签名必然不匹配，S3 拉取必然失败。

反证是一个能区分两种情形的实验。往桶里放一个前缀之外的对象 `zzz-outside/decoy.userdb.txt`：

- 若查询串到达服务端，前缀过滤生效，诱饵对紫毫不可见，拉取正常
- 若查询串被丢弃，服务端返回全部对象，诱饵的键因不匹配前缀而被 `substr` 截出错误的名字，随后 `Get` 必然 404，整个拉取失败

实测结果是诱饵不可见且拉取正常。此外还有一个更直接的判据：签名覆盖规范查询串，服务端收不到查询串时重建出的签名必然不同，会返回 403 而非 200。

尽管如此，`HttpRequest` 现在显式请求 `lpszExtraInfo` 并拼回请求目标。理由不是结论正确，而是这个行为在文档里没有保证，而 SigV4 恰好签了查询串——一旦哪天行为改变，症状会是所有列举一齐签名失败。消除脆弱依赖比争论当前行为更有价值。

### 卸载时 `RegDeleteKey` 会摧毁另一个发行版

成因判定有误，但**相邻的问题真实存在**且已修复。

结论认为 `imesetup.cpp` 中 `RegDeleteKey(HKEY_LOCAL_MACHINE, RIME_REG_KEY)` 会删掉共享的 `Software\Rime` 父键，连带毁掉官方小狼毫。实际上 Win32 的 `RegDeleteKey` 在目标键仍有子键时会失败，因此另一个发行版存在时它删不掉父键，反而是在清理空父键。

真正危险的是 NSIS 的 `DeleteRegKey`，它**默认递归**。安装脚本里那两处已改为只删本产品分支，父键改用 `/ifempty`。

### S3 端点中的端口

结论认为 `HostFromEndpoint` 返回的 host 含端口，会传给 `WinHttpConnect` 而导致连接失败。实际上该结果只用于 SigV4 的规范 host，连接用的是 `HttpRequest` 内部独立解析的结果。而 SigV4 要求签名的 host 与实际发出的 `Host` 头一致，非默认端口本就应当保留。

但它点到一个真实边界：显式写出与协议默认值相同的端口（`https://host:443`）时 WinHTTP 会将其从 `Host` 头中省略，签名就对不上。现在只剥离这种重复端口。

### 关闭设置窗口会让 WebView2 创建回调访问已销毁对象

结论认为：`SettingsPanel.cpp` 的环境创建与控制器创建完成处理器都捕获裸 `this`，而 `ShowSettingsPanel` 中的面板是栈对象，因此在 WebView2 创建期间关闭窗口会让两个回调通过已经销毁的对象执行。

判定为**不成立**。WebView2 完成处理器经 UI 线程的消息泵到达；`ShowSettingsPanel` 的栈对象一直存活到消息循环退出，而 `GetMessageW` 只在没有其他待处理消息时取出 `WM_QUIT` 并返回 0。因此已经排队的完成处理器会在栈对象仍存活时得到分派。窗口销毁后 `m_hWnd` 为 null，完成处理器里的 `PostMessageW` 与控制器创建会失败并返回，不会把调用变成对已析构 `this` 的访问。

## 反复出现的缺陷模式

### 「没有数据」与「拿不到数据」共用一个返回值

这一模式会直接造成数据丢失，所有后端与存取路径都必须保留以下区分：

- **对象不存在与对象拿不到必须可区分。** `SyncBackend::Get` 使用 `FetchResult{ kOk, kNotFound, kError }`；只有确定的 404 可以触发数据密钥建立，网络故障、鉴权失败与不完整响应都不得当作缺失，否则新密钥可能覆盖旧密钥并让全部密文永久失去解密路径。
- **文件为空与文件读不到必须可区分。** `ReadFileBytes` 单独上报失败；数据密钥对象为空属于存储损坏，不属于缺失。
- **空内容与可发布状态必须可区分。** 零字节词库快照不是值得发布的状态，不得加密并上传覆盖远端的有效对象。
- **空结果集与结果拿不到必须可区分。** 列表正文解析失败或 HTTP 响应正文中途截断都表示本轮失败；只有完整响应中成功解析出的空列表才表示远端没有对象。
- **唯一对象创建与普通覆盖必须可区分。** `keys/dek.bin` 只能走 `PutIfAbsent`；事前 `Get` 加普通 `Put` 不是原子操作，两台设备能在两次调用之间同时通过检查并互相覆盖。条件不满足必须返回 `kAlreadyExists`，且保证旧对象没有被修改。

**检查任何后端、文件路径、响应读取器与解析器时，都要沿调用链确认「确实没有数据」拥有独立于「无法取得完整数据」的表示。**

### 拉取失败不能留下半轮状态

远端对象必须先整批下载、认证、解密和格式校验，全部成功后才可触碰 Rime 的同步目录。本地提交也必须先完整写入同目录临时文件；任一替换失败时，反向恢复本轮已经替换的目标。若操作系统拒绝回滚或备份清理，必须返回独立的 `kRecoveryRequired` 并保留 `.hare.bak.*` 恢复材料，不能把部分提交或残留旧内容伪装成普通成功。逐对象“下载一个、覆盖一个”会让后续网络错误或损坏对象把失败的一轮留成新旧混合状态。

### 服务宣称条件写不等于真的执行

开发机手工验收记录（2026-08-19）：对真实服务并发验证时，坚果云 WebDAV 对同一 URL 的两次 `If-None-Match: *` PUT 依次返回 201、204，并让第二次内容覆盖第一次；当时线上部署的旧 Worker 连非法条件值也返回 200 并覆盖。两者都会让仅凭 `2xx` 判断的客户端把不安全覆盖误报为创建成功。

同日的开发机手工验收中，Cloudflare R2 直连的产品后端验证通过：两个并发 S3 条件 PUT 恰好得到一个创建和一个已存在，重复写仍为已存在，GET 保持胜者内容。更换 R2 凭据前，产品后端与独立 PowerShell signer 都得到同一个 `403 AccessDenied`；更换为具备对象读写/列举权限的凭据后两者立即通过，因此该次 403 属于授权配置，不是签名路径缺陷。这项线上验收不属于仓内自动测试。

同日部署新版 Worker 后的手工线上复验通过：认证后的 `/capabilities` 精确返回 `hare-worker/1 conditional-put`，对保留探针的第二次条件 PUT 返回 412，随后 GET 内容不变；验证前后的 `keys/dek.bin` 状态均为 200 且字节完全一致。

因此 WebDAV 在正式数据密钥写入前，必须用同一 `keys/` collection 下固定的 `keys/conditional-put-v1.bin` 非敏感对象验证第二次条件 PUT 得到 412 且原内容不变；验证失败就拒绝 `PutIfAbsent`，不能回退到普通 PUT。Worker 必须先从认证后的 `/capabilities` 取得精确的 `hare-worker/1 conditional-put` 协议标记，再对同一保留对象做行为验证；旧部署返回 404，新客户端据此在向 `keys/dek.bin` 发送 PUT 前失败。

### 有规范的格式不写临时解析器

XML 实体解码、百分号编码与 URL 组件划分都有明确规范；对象名、路径与 URL 边界的缺陷集中在这些格式的手写处理中。对有规范的容器、归档、字符集、实体与 URL，先采用已有实现；只有平台提供相应原语时才在项目中自行组合，不用子串、正则或不完整的转义表代替规范实现。

实现选择必须同时遵守 [DESIGN.md](DESIGN.md) 的「依赖边界」：链入 `hare.dll` 的路径只用系统原语，`HareDeployer.exe` 与 `HareServer.exe` 可使用满足该层许可及交付条件的仓内实现，构建工具与 `worker/` 可直接采用其生态中的成熟实现。

### 验证只证明了结果，没证明路径

一处硬编码让紫毫读取了官方小狼毫的注册表键。同步测试全部通过，因为两个键**恰好指向同一个目录**——缺陷被完全掩盖。

后来的验证改为把两个键指向不同位置再观察文件落点。**设计验证时要能区分「碰巧对」和「真的对」。**

### 观测手段本身有偏差

设置面板的截图看起来内容溢出窗口右缘，像是尺寸算错了。实际上窗口是对的：截图脚本所在的进程不感知 DPI，Windows 于是把 `GetWindowRect` 的结果按缩放比例缩小报给它（150% 下 1380 报成 920），脚本据此开了一张小位图，`PrintWindow` 便只画进了左上角那一块。

**验证 DPI 相关的东西时，观测进程必须与被观测进程处在同一 DPI 语境**（截图脚本先调 `SetProcessDPIAware`）。同理，任何「看起来不对」的现象，先确认不对的是被测对象而不是量具。

### 改动散落在肉眼扫不到的地方

更新源的地址存在 `.rc` 里，是十六进制裸字节，扫代码看不出来。因此改完注册表路径之后，紫毫仍会去下载**官方小狼毫**并覆盖安装自己。

现在改为在代码中显式设置 feed 地址，其优先级高于资源，资源里的旧地址不会被意外采用。共存所需的全部标识清单见 [DESIGN.md](DESIGN.md)。
